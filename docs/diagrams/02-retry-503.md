# Retrying when the server returns 503

The mock server deliberately fails about 10% of requests with a 503. This diagram shows why the partner writes no code for it.

```mermaid
sequenceDiagram
    autonumber
    actor Partner as Partner application
    participant Pipe as RequestPipeline
    participant Retry as core/retry.ts
    participant Clock as Clock
    participant Tr as NodeHttpTransport
    participant Chaos as chaos.ts
    participant H as handlers/claims.ts

    Partner->>Pipe: create a claim, idempotencyKey = K
    Pipe->>Tr: attempt 1, Idempotency-Key K
    Tr->>Chaos: POST /api/v1/claims
    Chaos->>Chaos: random draw below failureRate
    Chaos-->>Tr: 503 with Retry-After 1
    Note over Chaos,H: Chaos runs BEFORE the handler, so no claim was created.<br/>A 503 leaves no side effect behind

    Tr-->>Pipe: 503
    Pipe->>Retry: isRetryableStatus(503)
    Retry-->>Pipe: true
    Pipe->>Retry: computeDelayMs(attempt 0, retryAfter 1000)
    Retry-->>Pipe: 1000 plus a random 0 to 250
    Pipe->>Clock: sleep(delay, signal)
    Note over Clock: sleep listens to the abort signal,<br/>so cancelling takes effect immediately instead of after the backoff
    Clock-->>Pipe: wait elapsed

    Pipe->>Tr: attempt 2, STILL Idempotency-Key K
    Tr->>Chaos: POST /api/v1/claims
    Chaos->>H: allowed through this time
    H->>H: look up Idempotency-Key K, not present
    H->>H: create CLM-000001
    H-->>Tr: 201 Claim
    Tr-->>Pipe: 201
    Pipe-->>Partner: Claim

    Note over Pipe: If all 1 + maxRetries attempts fail,<br/>it raises ApiError or NetworkError carrying attempts
```

## The backoff formula

`delay = random(0, min(8000, 250 × 2^attempt))`

| Wait | Ceiling | Actual range |
|---|---|---|
| After attempt 1 | 250ms | random 0–250ms |
| After attempt 2 | 500ms | random 0–500ms |
| After attempt 3 | 1000ms | random 0–1000ms |

When the server sends `Retry-After`, the wait becomes `retryAfterMs + random(0, 250)`.

## What to take away

- **The randomness matters more than the doubling.** Fixed backoff wakes every client on the same beat and dumps load onto a server that is already struggling. Doubling only spreads attempts out in time; it does nothing to break the synchronisation between clients.
- **The same `Idempotency-Key` appears at step 2 and step 12.** If the first attempt did reach the handler before the connection dropped, the retry gets the original claim back instead of creating a duplicate.
- **Not every failure is retried.** 429, 502, 503, 504, socket errors and timeouts are. 400, 403, 404, 409, 413 and 422 raise immediately, because retrying cannot change the outcome.
